# LongMemEval cleaned-S held-out retrieval protocol (frozen 2026-09-26)

This was a **project-untuned public test** for the first paired comparison, not an independent human review or a production score. The questions have now been used for model selection; do not tune retrieval on them and continue calling them fresh held-out data.

## Source and input

- Official project: https://github.com/xiaowu0162/LongMemEval
- Official cleaned dataset: https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned
- File: `longmemeval_s_cleaned.json` (about 277 MB), **not** `longmemeval_oracle.json`. The latter contains evidence sessions only and cannot measure retrieval among distractors.
- The dataset page marks the cleaned release MIT; preserve attribution and the license. Keep raw data outside Git. Before any run, record the dataset revision, byte size and SHA-256; fail rather than silently accept a changed file.

## Frozen selection and replay

Use all 500 instances in official file order for the definitive retrieval comparison. A small first-N smoke is allowed only to validate the adapter and is never reported as the benchmark result. Exclude the 30 `_abs` questions from evidence retrieval scoring; report their count separately. Do not exclude other questions based on answer, length, or observed result. If an instance lacks usable `has_answer` labels or has malformed sessions, report its ID and reason and stop before producing a headline score.

For each instance, create a fresh isolated store. Replay `haystack_sessions` chronologically as provided, one turn per memory, preserving role and session ID. Keep the query after all writes. Map returned memory IDs back to original session/turn indices. Never feed `has_answer`, `answer_session_ids`, `answer`, or question type to storage, retrieval or the local model. These fields are scorer-only. No oracle evidence expansion, summaries, graph edges, future turns, or timestamp restoration beyond what the storage interface supports. If the storage interface truncates or transforms text, record it.

## Arms and metrics

Compare unchanged TF-IDF `precision` Top-5 against one English-capable local embedding provider on the **same written store, corpus, candidate path and Top-5 budget**; alternate arm order per question. Do not substitute the cached Chinese BGE model and call that an English semantic test. Pin model repository/revision, files hash and size, device and library versions before running. If no suitable model is available locally, run only the TF-IDF baseline and mark the semantic arm pending; a download is a separate, measured onboarding cost.

Primary metric: fraction of eligible questions with at least one official `has_answer` turn in Top-5. Also report all-evidence-turn recall, evidence-session Top-5 hit, per-question paired gains/losses, and breakdown by official question type. These are **official evidence retrieval** metrics, not relevance precision, answer accuracy, or the official LongMemEval QA score. Official evidence may be incomplete; do not call other returned turns false positives. No final-answer generation until retrieval is inspected and the protocol is explicitly extended.

## Cost, limits and release gate

Record corpus turns and characters, cold model load, corpus encode/setup, store-write time, warm query p50/p95, process working-set before/after, local disk bytes, download bytes/time, and paid API calls. Separate one-time onboarding from per-query time; do not infer electricity cost from wall time. Repeat the paired retrieval run three times where affordable, preserving the same question order and alternating arm order. Report failures and full regression result.

Do not change SDK/MCP defaults solely on this public benchmark. Promotion additionally requires the paused 96-row human review (filled by a human), Chinese and graph-negative checks, and a measured user time/price benefit. Public benchmark exposure in foundation-model training is unknown; “project-untuned” does not mean statistically independent of all prior knowledge.
